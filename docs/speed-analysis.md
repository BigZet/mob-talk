# Скорость ответа моба: где уходит время и что ускорить

Разбор на коммите `cc3d089` (20 октября 2026). Только анализ, кода не менял.
Числа — из логов игры и самотеста (`minecraft/logs`, `%LOCALAPPDATA%\MobTalk\selftest`) и из живой пробы
с реальным ключом OpenRouter на тех же промптах, что собирает мод (харнесс против `build/classes`, игра закрыта,
Whisper-сервер уже был запущен на CUDA). Всего около 30 запросов, около 2 центов.

## 1. Что видно в логах

| Сценарий (самотест, 20 октября) | Время от вопроса до ответа |
|---|---|
| Первая встреча с коровой (биография внутри ответа) | 12–17 с |
| Житель, вторая реплика | 8 с |
| Угроза, оскорбление (знакомый моб) | 7 с |
| Инициатива Ольги (LLM + начало озвучки) | 5–8 с, восемь реплик подряд |
| Путь через Whisper (TTS вопроса + Whisper + LLM + TTS) | 15–25 с |

Всего в логах: 4 раза «превышено время ожидания», 2 раза HTTP 429, 8 раз «не написал биографию (ответ обрезан)»,
0 отклонённых валидатором ответов (исправления с повторной отправкой почти не случаются).
В игре `requestTimeoutSeconds` = 70, `reasoningEffort` = minimal, `historyTurns` = 33, `maxReplyWords` = 70,
TTS через Venice (`tts-elevenlabs-turbo-v2-5`, баланс 0,10 — после проверки баланса сессия уходит на OpenRouter).

## 2. Живая проба по стадиям (знакомый житель, промпт как в игре: 4,2 тыс. токенов, ответ 170–280 токенов)

| Стадия | Измерено |
|---|---|
| Whisper large-v3, CUDA, beam 5, 13 с речи | 1,25–1,5 с (в игре при нехватке VRAM медленнее) |
| LLM `gpt-6-luna`, заголовки ответа | 0,8 с |
| LLM, первый токен **без** рассуждений | 1,2–1,8 с |
| LLM, первый токен **с** рассуждениями (minimal всё равно думает 48–123 токена в 7 из 10 проб) | 2,8–4,6 с |
| LLM, от первого токена до закрытия поля `reply` | +0,5–0,9 с (перед reply идёт `assessment`) |
| LLM, хвост JSON после reply (socialIntent, action, bargain, deal, quest, newFacts, thought, gesture) | +0,9–1,0 с |
| LLM, первая встреча: биография внутри ответа (514 токенов) | reply закрыт на 3,9 с, весь JSON на 7,0 с |
| TTS eleven-flash через OpenRouter, первые 0,4 с звука | 0,7 с на тёплом соединении, 2,6 с на холодном |
| TTS, вся реплика 13 с звука | 1,8 с (качается во время воспроизведения) |
| Кэш промпта OpenAI (повтор того же промпта) | 4176 токенов из кэша, цена ниже в 4,6 раза, задержка та же |

Итого для голосового вопроса знакомому мобу: Whisper 1 с + LLM 3 с + озвучка почти вся перекрыта хвостом JSON
≈ 4–4,5 с в лучшем случае; когда модель решила подумать — 5,5–6,5 с; первая встреча — 8–9 с. Это и есть
наблюдаемые 5–8 с. Текст показывается только после полного JSON и до 0,4 с звука в буфере
(`ConversationEngine.prepare` ждёт `llm.respond` целиком, озвучка стартует раньше по `completedReply`).

Другие модели на том же промпте (для справки, первый токен / весь JSON): `deepseek-v4.1-flash` 1,0–3,4 с / 1,8–4,2 с;
`claude-haiku-5.5` 1,9–3,9 с / 3,3–5,4 с (6,7 тыс. токенов промпта в его токенизаторе);
`gemini-3.5-flash-lite` — reply закрыт на 1,3 с, но думать отключить нельзя, JSON только на 5,5 с;
`gpt-5.6-luna` 2,4–7,2 с. Выигрыша над `gpt-6-luna` без рассуждений нет.

## 3. Откуда зависания на 60–90 с

1. Один статический семафор на 3 запроса (`OpenRouterConversationClient.IN_FLIGHT`) делят реплика игроку,
   два очевидца, биография заранее, болтовня деревни, объявления, сводки, рефлексия и хроника. Вопрос игрока
   может стоять за ними весь `requestTimeoutSeconds` (70 с), потом «превышено время ожидания».
2. Нет таймаута на первый токен: зависший поток провайдера ждут все 70 с; до трёх исправлений идут в тот же срок.
3. 429 на ключе повторяются через 1,5 и 3 с, биография при обрезке (1200 токенов) уходит повторно.
4. Пока проверка баланса Venice не ответила, первая озвучка сессии сначала идёт в Venice; модель
   `tts-elevenlabs-turbo-v2-5` там отдаёт MP3 целиком, без потока (`format()` = mp3), это плюс 1–2 с к каждой реплике,
   если Venice когда-нибудь пополнят.

## 4. Что ускорить (по убыванию выгоды на усилие)

| # | Мера | Ожидаемый выигрыш | Цена / качество | Усилие |
|---|---|---|---|---|
| 1 | Слать `reasoning.effort = "none"` явно (сейчас «none» в конфиге значит «ничего не слать», и модель думает по умолчанию; «minimal» всё равно думает в 70 % случаев) | 1,5–2,5 с на большинстве реплик | Реплики в пробе не хуже; цена чуть ниже | 1 строка в `body()` + значение по умолчанию |
| 2 | Отдавать текст и голос по закрытию поля `reply`, хвост JSON (действия, торг, факты) применять после | 0,9–1,0 с на каждой реплике, 3 с на первой встрече | Если валидатор отвергнет хвост (в логах 0 случаев), реплика уже прозвучала, намерения просто не применяются | Средне: разделить `prepare` на две фазы |
| 3 | Свой слот для вопроса игрока: фон (биография, сводки, болтовня, хроника) не занимает последний из 3; очевидцы не стартуют, пока игрок снова говорит; таймаут первого токена ~10 с с одним повтором; `requestTimeoutSeconds` 70 → 30 | Убирает хвост 60–90 с и ожидания в очереди | Фон иногда подождёт | Мало-средне |
| 4 | Whisper `large-v3-turbo` вместо `large-v3`, beam 5 → 2–3 | 1,3 с → ~0,5 с, в игре под нагрузкой заметнее | Чуть ниже точность на русском; есть подсказки из мира | Настройка |
| 5 | `assessment` укоротить до одной фразы или перенести после reply | 0,3–0,6 с | Возможна чуть менее собранная реплика; проверить живыми пробами | Малое |
| 6 | Биографию при первой встрече не включать в ответ: короткий ответ сразу, история — фоновым запросом после (как сейчас для отменённых prefetch) | 3 с на первой встрече (7 → 4 с) | Первая реплика знает меньше о себе; второй запрос стоит тех же денег | Среднее |
| 7 | Греть TTS и LLM соединение при входе в мир (крошечный запрос), Venice TTS без PCM-потока не использовать, ttsProvider = openrouter, пока Venice пуст | 2 с на первой реплике сессии, 1–2 с на каждой при Venice MP3 | Нет | Малое |
| 8 | Промпт: статичные правила (`RULES`, `VOICE`, карточка вида) в начало, изменчивое (настроение, ситуация, память, слухи) в конец; подрезать с 12,7 тыс. символов | Цена ниже в 4 раза за счёт кэша; скорость заметно только на длинных памятях (0,2–0,5 с) | Нет | Среднее, много тестов на тексты промпта |
| 9 | Озвучивать по предложениям, пока reply ещё стримится | ~0,3 с | Возможны стыки между фразами | Среднее, не стоит пока |

Не помогает: смена модели (см. раздел 2), снимок экрана (десятки килобайт, дешёвый `detail: low`),
сам Jev (1,5 с лимит, стоит не на пути ответа), распознавание на CPU.

## 5. Рекомендация

Сделать 1, 3 и 4 сразу (настройки и пара строк, выигрыш 2–3 с и конец зависаний), затем 2 и 7 одним треком
(ещё около 1–2 с и мгновенный старт первой реплики), 5 и 6 проверить живыми пробами качества. Цель — 2,5–3 с от
отпускания клавиши до голоса знакомого моба и 4–5 с на первой встрече.

## 6. Что сделано (20 октября, слито в main)

Сделаны пункты 1–4: `reasoning.effort = "none"` передаётся явно; реплика и её голос уходят в чат и динамик
по закрытию поля `reply`, а хвост применяется после (кроме торговцев и очевидцев); три полосы запросов
(игрок, очевидцы и инициатива, фон); `firstTokenSeconds` = 12 с в F7 с одним повтором; Whisper `large-v3-turbo`, beam 3.
Конфиг переходит на schemaVersion 3 и заменяет только старые значения по умолчанию. В логе на каждый ответ
пишется строка `Mob Talk timing`. Не сделаны пункты 5–9.

Самотест: семь полных прогонов (шесть с ускорением, один на старом main). Последний дал 139 OK и 1 FAIL:
очевидец-корова не уложилась в ожидание этапа, но реплику сказала. Этапы «сон вдвоём» и «букет невесты»
укреплены: с быстрыми ответами соперник успевал лечь во вторую кровать, а ванильный житель на миг убирает цветы из руки.
Время ответа в игре сильно зависит от часа: «line out» от 2,5 до 12 с при той же сборке.
